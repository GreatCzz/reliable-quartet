# rscore：把"可靠四叶树"计分接入 aster2 的迭代框架

> 目标：**不重写搜索循环**，只实现 aster2 要求的 `STEPWISE_COLORABLE` 着色接口
> （`elementSetTaxonColor` / `elementClearTaxonColor` / `elementScore`），
> 让框架自带的 placement / 约束 DP / 线程池去搜索，得到我们的基准求解器。

## 计分怎么接进去

框架对每个物种树内部节点把类群染成三色：`2 = 树下子簇`、`1 = 姐妹子簇`、`0 = 其余`。
我们的分数天然分解到每个内部节点：

```
score = Σ_{S 内部节点 v} F(l_v, r_v)
```

所以只要让 `elementScore(iElement)` 返回 `F(颜色2的叶子, 颜色1的叶子)`，
框架把各节点的分数加起来就正好等于官方分数。**不需要 2-1-1 那种 ASTRAL 式分解。**

## 颜色 → 簇映射

| 颜色 | 含义 | 参与 F 的哪一侧 |
|---|---|---|
| 2 | 放置点下方的子树 | l |
| 1 | 姐妹子树 | r |
| 0 | 其余 | 不参与（四叶树的 LCA 在别处） |

`F` 对 l/r 对称，所以顺序无所谓。

## 已知风险

- placement 是启发式，收敛性与分数不保证；
- R1 非增量版在 9000×1000 上会非常慢（每次评估 O(m·n)），只用于小实例验证；
- 内存：每个元素一份 `nTaxa` 颜色数组（1000×10000 = 10 MB），可接受。

## R1 验证记录（2026-10-20）

| 验证 | 结果 |
|---|---|
| C++ `reliableScore` vs Python 公式（30 组随机多叉树 + 随机三色） | 全部一致（`src/rscore_selftest.cpp`） |
| 4 类群合成例子（3 棵 `((a,b)S,(c,d)S)`） | 框架分数 3，输出 `(((c,d),b),a)`（未 rooting 意义下即 ab\|cd） |
| rep01 抽 40 类群 × 40 棵树 | 用时 **0.23 s**；框架报告 14773，Python `fast_formula` 独立打分 **14773** ✅ |

### 已知问题 / 下一步

- R1 非增量：每次 `elementScore` 是 O(n)，全量（9000×1000）会慢几个数量级，必须做 R2 增量版；
- `elementScore` 已改为 `thread_local` 缓冲（框架会并发调用），成员 `scratch_` 已闲置；
- 调试图标：环境变量 `RSCORE_DEBUG=1` 会打印前 10 次打分。

## R2 之后：全量求解器（`solver/`）

框架的放置过程需要 O(m²) 次评分，而我们每次评分是 O(n)（不是 ASTRAL 那种 O(1) 增量），
所以框架只适合中等规模基准。全量走本地搜索：

```
solver/solver.cpp
  score = Σ_{S 内部节点} F(左孩子簇, 右孩子簇)        # 与 rscore.hpp 同一个 F
  缓存 cache[内部节点][基因树]
  NNI：对内部边 (u→v)，交换 u 的另一个孩子 a 与 v 的一个孩子
        ⇒ 只有 u、v 两个节点的 F 变化 ⇒ 每次候选 O(2·T·|g|)
```

编译与用法：

```bash
cd solver
g++ -std=c++20 -O3 -march=native -fopenmp -I ../aster2/src solver.cpp -o solver
./solver -s 初始树.tree -i 基因树.txt -t 32 --sweeps 5 -o 输出.tree
```

### 已验证

| 验证 | 结果 |
|---|---|
| 初始分数 vs Python `fast_formula`（40 类群 × 40 树） | 18861 = 18861 ✅ |
| NNI 5 轮后 | 18861 → **22825**（+21%），Python 独立打分 22825 ✅ |

### 实测（2026-10-20）

**500 类群 × 100 棵树**（用同一套 C++ 打分器，Python 独立复核）

| 树 | 分数 |
|---|---|
| 簇共识 v0（限制到同样 500 类群） | 612,537,698 |
| aster2 框架跑出的基准树 | 588,288,437 |
| 在基准树上做 3 轮 NNI | **1,273,377,908**（+116%） |

**全量 10000 类群**（先取 200 棵树做搜索，最后用全部 1000 棵复核）

| 阶段 | 分数 |
|---|---|
| 簇共识 v0（200 棵树） | 131,794,861,532,454 |
| NNI 第 1 轮（3904 次移动） | **156,166,735,757,918**（+18.5%） |
| 单轮耗时 | 207 秒（32 线程） |

### 全量第二轮（1000 棵树）

从 v1 出发再跑 3 轮 NNI：

| 轮次 | 移动数 | 增量 | 总分 |
|---|---|---|---|
| 初始 | — | — | 632,949,050,483,880 |
| 1 | 1556 | +2.26e10 | 632,971,671,919,432 |
| 2 | 1355 | +1.21e10 | 632,983,749,189,815 |
| 3 | 1227 | +1.24e10 | **632,996,196,599,254** |

增量已经很小（+0.007%）→ **从簇共识出发的 NNI 已收敛**。

### 关键发现：初始树决定一切（500 类群对照）

| 初始树 | 初始分数 | NNI 收敛后 |
|---|---|---|
| 随机二叉 | 469,164,786 | 469,169,336 |
| 簇共识 v0 | 612,537,698 | 736,903,551 |
| **aster2 框架（放置算法）** | 588,288,437 | **1,273,377,908** |

同一个 NNI、同一个打分器，三者差 2.7 倍。说明**框架的"逐个放置"能进入好得多的盆地**，
而 NNI 只能在其附近微调。⇒ 全量要做大提升，必须换更好的初始构造，而不是继续 NNI。
